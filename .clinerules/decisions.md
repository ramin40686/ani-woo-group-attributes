# Group Product Attributes — Decisions

> **Phase 2A.3 redesign (2026-11-25).** The owner clarified the product concept: GPA is a
> **reusable Global WooCommerce Attribute Template Manager** (groups are templates of
> Global Attribute definitions; loading a group adds **native** WooCommerce attribute rows;
> the product's native attribute data is the single source of truth; all attributes render
> through the standard WooCommerce/Blocksy Additional Information tab). This redesign
> **supersedes** the previous value-selection / separate-renderer architecture. New
> decisions **D28–D39** record the clarified requirements. The affected previous decisions
> are preserved below in the **Superseded / Obsolete** table with their status, the
> replacing decision, and the architectural reason. The full supersession matrix and the
> Phase 2A.2 corrections applicability assessment are in
> `reports/2026-11-25-phase-2a-3-native-attribute-template-redesign.md`. Historical
> decision text is preserved verbatim in the superseded table.

| D28 | **GPA groups are templates of Global Attribute definitions (core product concept):** a GPA group is a reusable template containing an ordered list of references to existing WooCommerce **Global Attribute definitions** (taxonomy-based `pa_{slug}` attributes). A group defines **which attributes should be added to a product**; it does **not** define the product's actual attribute values. Groups reference attribute **definitions, not terms**, and never store/duplicate/manage terms or product-specific values. Groups contain **Global Attributes only** — Custom product attributes are not group members, and there is no custom-attribute aggregation / group membership / vocabulary subsystem. Supersedes the three-tier A/B/C value model and the D14 "both kinds participate in groups" contract. | Owner decision, 2026-11-25 (Phase 2A.3) |
| D29 | **Loading a group adds native WooCommerce attribute rows:** the Load operation inserts the group's Global Attribute definitions into the product's **native** WooCommerce attribute collection (Product Data → Attributes), reusing the native `woocommerce_add_attribute` row-insertion mechanism so the result is equivalent to adding those attributes through WooCommerce's normal native workflow. GPA creates **no** parallel product-attribute data structure and writes product attributes **only** through the native save lifecycle. The admin then uses native controls to select terms, add values, remove, reorder, and edit. | Owner decision, 2026-11-25 (Phase 2A.3) |
| D30 | **No persistent group assignment or attribute provenance:** once a group is loaded, its attributes become ordinary native WooCommerce product attributes; there is **no** behavioral distinction between a GPA-loaded attribute, a manually-added Global Attribute, and a manually-added Custom Attribute. The product's native attribute data is the **single source of truth**. The previous metadata contracts `_ani_gpa_assigned_groups` and `_ani_gpa_selected_values` are **removed** from the active architecture; no GPA-specific product metadata is introduced, and no provenance (which group supplied an attribute) is stored. | Owner decision, 2026-11-25 (Phase 2A.3) |
| D31 | **Group attribute ordering:** within the group editor, the admin configures the order of attributes inside a group; this order determines the **initial insertion sequence** when the group is loaded. The **final** attribute order on an individual product is controlled **exclusively** by the native WooCommerce Product Data → Attributes interface. GPA does **not** impose group ordering on the frontend and does **not** override the product's native attribute order. **Global ordering of GPA groups is not a required feature.** | Owner decision, 2026-11-25 (Phase 2A.3) |
| D32 | **Custom Attributes remain native:** Custom Attributes are fully supported as native WooCommerce product attributes. They are **not** GPA group members, are **not** loaded through GPA groups, and have **no** separate GPA management workflow. They are added/managed only through the native product editor and **must receive the same frontend presentation treatment** as Global Attributes (same Additional Information tab, same table, same uniform style). | Owner decision, 2026-11-25 (Phase 2A.3) |
| D33 | **Frontend rendering is native only:** all product attributes (GPA-loaded Global, manual Global, manual Custom) are displayed through the **standard WooCommerce/Blocksy product attribute presentation** in the existing **Additional Information** tab. There is **no** separate GPA attribute table, **no** GPA group heading, **no** group-category heading, **no** grouping by source group, **no** separate GPA frontend renderer, **no** custom Blocksy product layer for GPA output, **no** configurable GPA frontend location, and **no** native-table suppression. The customer must not see or need to know how an attribute was added. The displayed order follows the product's native attribute order. Supersedes D16 (Blocksy custom layer), D17 (native-table hide), and the D27 empty-group frontend model. | Owner decision, 2026-11-25 (Phase 2A.3) |

| D34 | **Uniform table presentation:** GPA provides three presentation styles — `default` (preserves the standard WooCommerce/Blocksy appearance), `minimal`, and `boxed`. The selected style applies **uniformly to ALL product attributes**, regardless of whether the attribute is Global or Custom or whether it was loaded through GPA or added manually; it must not depend on group membership or provenance. The presentation remains lightweight and introduces **no** duplicate attribute tables and **no** unnecessary frontend JavaScript. The recommended mechanism is CSS-only (styling the native `shop_attributes` table); the final mechanism is a Phase 2B/3 decision. | Owner decision, 2026-11-25 (Phase 2A.3) |

The live menu is not changed as part of the documentation task. | Owner decision, 2026-11-25 (Phase 2A.3) |

| D24 | **Group status policy (U11):** groups with status `publish` or `draft` may be selected and assigned to products. | D25 | **Custom-attribute aggregation product-status policy (U12):** only products with `post_status = 'publish'` may contribute custom-attribute values to the store-wide group vocabulary. Products in any other status (at minimum `draft`, `pending`, `private`, `future`, `trash`) must not contribute values. The status restriction is applied to the posts table in the `wp_posts` ⋈ `wp_postmeta` JOIN. This decision does not introduce catalog cleanup or migration behavior. | **Obsolete** | D28 | The custom-attribute aggregation subsystem (raw SQL, transient cache, product-status scope) no longer exists because groups contain **Global Attributes only** and draw no custom-attribute vocabulary. | D26 | **Stale selected-value lifecycle policy (U13):** a selected value may become stale if the corresponding attribute or value is later removed or changed on the product. Render time: revalidate every selected value against the current product attributes; ignore stale values; stale values are not rendered, do not make a group renderable, and do not suppress the native WooCommerce attributes table. Save time: revalidate submitted values; reject invalid or stale submitted selections; persist only accepted valid selections. Storage: do not automatically delete previously stored stale selections; preserve them until an explicit valid save replaces the submitted selection set; no automatic background cleanup or migration. Rendering is read-only (no metadata modification, no deletion of stale references, no rewriting of group assignments, no destructive cleanup). | **Obsolete** | D28, D30, D33 | There are **no** per-product "selected values" in the new model (values are managed natively; `_ani_gpa_selected_values` is removed). The stale-**reference** concern that remains (a group's Global Attribute reference becoming stale after a rename/delete) is handled by the new reference-integrity contract (spec §3.3), not by this selected-value lifecycle. |
| D27 | **Empty-group behavior (definitive):** a group may be assigned to a product without selecting any values — a valid administrative state; the assignment must not be rejected solely because no values have been selected. Frontend: a group with no selected values (or no currently valid selected values) must not produce a frontend table — no empty tables, no headings or group labels without actual attribute rows; groups whose selected values are all invalid or stale are skipped. Native table (D17 preserved): the native WooCommerce attributes table remains visible by default; GPA may hide it only when valid, renderable GPA content exists and the relevant setting permits hiding; an assigned group with no selected values, and invalid or stale selected values, do not count as renderable GPA content; if no valid GPA content remains, the native table must remain visible. | **Superseded** | D33 (and spec §4.4) | The old model treated a group as a **frontend table** with selected values. In the new model a group is a **template of attribute definitions**, not a frontend table, so the "empty group renders nothing / does not suppress the native table" rules no longer apply. The preserved analogue: a group with **no attributes** is a valid administrative state and, when loaded, inserts **no** rows (spec §4.4). The native table is always the output and is never suppressed (D33). |
